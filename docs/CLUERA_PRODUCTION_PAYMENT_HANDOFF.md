## October 23 continuation and checkout-window follow-up

The owner reports that **Continue existing checkout was greyed out**. Source review found that the button used the same busy flag as background account/status reads. A slow read disabled the explicit continuation action even when the original BOUND order was already displayed. The repair lets explicit continuation supersede a background read, then independently revalidates the account, merchant and exact original order before opening Checkout. Late responses cannot overwrite the current account. Authenticated checks after SDK loading are serialized so competing responses do not rotate the same session cookies concurrently. A failed SDK load or closed window can offer the original order again only after safe verification. Throttling preserves identity, honours a bounded retry delay and does not retry a payment. Live pending-state errors now remain HTTP 409 rather than being mislabeled as unavailable configuration.

A further server-side defect was verified against the installed `customer_auth_rate_limit` definition: checkout/status/history reads consumed the same **15-per-email, 15-minute** bucket as login and payment writes. Normal observation could exhaust that bucket. Authenticated billing reads now use a separate HMAC namespace, bounded to 90 per account/email and 120 per IP in the same durable fifteen-minute window, shared across Test/Live. Login and financial-write limits retain their original namespace and 15/60 limits. Recovery/owner checks precede these reads, RPC failures deny access, and no caller-controlled URL selects the rate policy. No SQL migration or secret change is needed. If the read allowance is exhausted, the displayed retry delay is a minimum; the existing fifteen-minute server window may require longer.

The credits endpoint also now returns already-rotated secure session cookies when a later throttle or balance read fails. Previously that error path discarded the successful Auth rotation, which could interrupt subsequent requests. Tests verify the new encrypted refresh cookie survives both failures without appearing in JSON. Genuine unauthenticated responses clear the session while preserving a separate pending email flow.

The default Checkout display window is **600 seconds (10 minutes)**. Optional server setting `CLUERA_CHECKOUT_WINDOW_SECONDS` accepts an integer from 60 to 1800; absent/invalid values use 600. No setting change is needed for ten minutes. It is passed to official Checkout and also tracked locally with a deadline. Closing/expiry performs bounded status checks and an independent read-only original-order proof when the binding remains eligible. **This timer does not cancel an order, release the financial lock or authorize another charge.** An attempted, authorized, malformed or uncertain order remains locked for canonical reconciliation. Only the existing authoritative resolution path can release a known binding; no speculative failed-order abandonment was added. Razorpay documents that an attempted order can remain attempted until capture. See [Checkout integration and order states](https://razorpay.com/docs/payments/payment-gateway/web-integration/standard/integration-steps/).

## Pause, rollback and future domain migration

To pause new sales, set `CLUERA_LIVE_CHECKOUT_ENABLED=false` and withdraw the affected catalog availability. Removing only public approval can still leave bounded testers eligible, so it is not the complete pause control. Preserve Live intake, scheduler, cancellation/history and Test processing for existing obligations. Do not kill durable receipt processing to hide an error.

Roll back only to an accepted **mode-aware** code revision compatible with the installed schema. Never drop the bank/provenance schema, switch banks under active usage, relabel Test grants, delete receipts or reverse financial state through code rollback. Uncertain commands remain locked for independent canonical review; an accepted cancellation request is not terminal cancellation. The migration's transaction rollback protects installation failure, not a later business rollback. Retain a tested database backup/restore procedure and named incident owner before public sales.

The staging origin can remain the initial site only with the merchant's required website approval. Later custom-domain migration needs a coordinated sales pause: exact Auth/cookie and Google/Supabase redirects, desktop links, CSP, Live profile and worker origin/audience, webhook destination and both deployments. Expect fresh sign-in because cookies are host-bound. Keep old receipt processing available during the transition; never use wildcard redirects or copy sessions between domains. Merchant IDs and ledger provenance remain unchanged. DNS alone does not migrate billing.

**Public readiness: NO until genuine payment, private security/provider, operations and release acceptance pass.** No payment, replacement order, capture/refund/replay, secret change, Live activation or public-sales approval was performed by this work.
